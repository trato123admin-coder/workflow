# Proyecto Final — Sistema Inteligente de Gestión de Casos, Documentos, Workflow y Caja Chica

**Versión:** 1.0  
**Fecha:** 23 de septiembre de 2026  
**Arquitectura objetivo:** Supabase / PostgreSQL + Storage + aplicación web responsive + motor de automatización + IA  
**Idioma inicial:** Español  
**Moneda configurable:** PEN por defecto  
**Zona horaria configurable:** America/Lima por defecto

---

## 1. Resumen ejecutivo

El proyecto consiste en una plataforma web empresarial para administrar de extremo a extremo:

- Clientes y sus datos.
- Casos individuales y casos recurrentes.
- Modelos de caso.
- Procesos y subprocesos.
- Estados y porcentajes de avance.
- Documentos requeridos, opcionales y alternativos.
- Plantillas Word.
- Reglas documentales.
- Generación automática de Word/PDF.
- Recomendaciones mediante Inteligencia Artificial.
- Historial y trazabilidad.
- Cotizaciones y comparación histórica.
- Asignación y seguimiento de analistas.
- Alertas de vencimiento y procesos estancados.
- Caja chica, ingresos, egresos, saldos y arqueos.
- Configuración visual y funcional.
- Monitoreo de servicios externos.
- Notificaciones mediante Telegram.

La arquitectura documental central es:

```text
CaseModel
   ↓
Process
   ↓
DocumentType
   ↓
Template
   ↓
DocumentRule
   ↓
AIRecommendation
   ↓
GeneratedDocument
```

La IA no reemplaza las reglas de negocio. El sistema combina:

```text
Reglas determinísticas
        +
Datos del caso
        +
Documentos existentes
        +
Historial
        +
Base de conocimiento
        +
Búsqueda semántica
        +
IA
        ↓
Recomendación explicable
```

# 2. Objetivos

## 2.1 Objetivo general

Construir una plataforma centralizada que permita gestionar casos, procesos, documentos y caja chica, reduciendo trabajo manual y mejorando trazabilidad, control y productividad mediante automatización e IA.

## 2.2 Objetivos específicos

1. Centralizar todos los casos y documentos.
2. Definir modelos reutilizables para cada tipo de caso.
3. Configurar workflows sin depender de código para cada nuevo procedimiento.
4. Recomendar automáticamente documentos apropiados.
5. Generar documentos Word/PDF a partir de plantillas.
6. Mantener versiones y auditoría completa.
7. Medir el avance de cada caso y proceso.
8. Identificar vencimientos y estancamientos.
9. Facilitar la gestión de caja chica.
10. Permitir dashboards configurables.
11. Mantener control de acceso por perfiles.
12. Integrar servicios externos mediante APIs.
13. Permitir operación responsive en escritorio, tablet y móvil.

# 5. Arquitectura documental

## 5.1 Conceptos

### CaseModel

Define la estructura reutilizable de un caso.

Ejemplos:

- Constitución de empresa.
- Modificación societaria.
- Poder.
- Contrato.
- Trámite notarial.
- Trámite registral.
- Legalización.
- Gestión documental recurrente.

### Process

Define una actividad o etapa necesaria dentro del modelo.

Ejemplo:

```text
Caso: Constitución de empresa

1. Recolección de información
2. Elaboración de minuta
3. Revisión
4. Firma
5. Trámite notarial
6. Presentación registral
7. Seguimiento
8. Cierre
```

### DocumentType

Representa el tipo lógico de documento.

Ejemplos:

- Informe.
- Contrato.
- Minuta.
- Carta.
- Poder.
- Oficio.
- Solicitud.
- Resolución.
- Anexo.

### Template

Es la plantilla física utilizada para generar el documento.

Debe soportar:

- DOCX.
- PDF base cuando corresponda.
- Variables.
- Versiones.
- Vigencia.
- Estado activo/inactivo.
- Responsable.
- Fecha de aprobación.

### DocumentRule

Determina cuándo un documento aplica.

Ejemplo:

```json
{
  "all": [
    {"field": "case.client.type", "operator": "=", "value": "empresa"},
    {"field": "case.model.code", "operator": "=", "value": "CONSTITUCION"},
    {"field": "process.code", "operator": "=", "value": "MINUTA"}
  ]
}
```

### AIRecommendation

Registra una recomendación concreta de documento para un caso/proceso.

Debe almacenar:

- Documento recomendado.
- Alternativas.
- Confianza.
- Razones.
- Reglas que activaron la recomendación.
- Evidencia histórica.
- Usuario.
- Modelo IA utilizado.
- Timestamp.
- Resultado de la recomendación.

### GeneratedDocument

Representa el documento efectivamente generado.

Debe almacenar:

- Caso.
- Proceso.
- Tipo documental.
- Plantilla.
- Versión.
- Usuario generador.
- Archivo Word.
- Archivo PDF.
- Datos utilizados.
- Estado.
- Hash opcional.
- Fecha de generación.

# 6. Modelo de datos PostgreSQL / Supabase

## 6.1 Convenciones

- PK: UUID.
- Fechas: `timestamptz`.
- Identificadores humanos: códigos únicos.
- Configuraciones flexibles: `jsonb`.
- Archivos: Supabase Storage.
- Auditoría: tablas append-only cuando sea posible.
- Todas las tablas principales deben incluir `created_at` y `updated_at`.
- Las eliminaciones críticas deben ser lógicas (`is_active`) en lugar de físicas.

La IA debe explicar:

# 24. RLS — Row Level Security

La seguridad debe implementarse en PostgreSQL/Supabase, no solamente en la interfaz.

## Administrador

Acceso completo según política empresarial.

## Analista

Puede:

- Ver casos asignados.
- Ver procesos de sus casos.
- Crear/actualizar información permitida.
- Subir documentos.
- Solicitar recomendaciones IA.
- Generar documentos.
- Consultar historial autorizado.

## Consulta

Solo lectura sobre la información autorizada.

## Caja Chica

Acceso a:

- Cuentas de caja.
- Movimientos.
- Soportes.
- Conciliaciones.
- Reportes de caja.

No debe poder acceder a documentación jurídica/empresarial fuera de los permisos definidos.

# 48. Cálculo de avance

El avance del caso debe calcularse a partir de los procesos.

Fórmula conceptual:

```text
Avance del caso =
Σ(avance del proceso × peso del proceso)
/
Σ(peso de procesos)
```

Ejemplo:

```text
Proceso A: 100% × 20%
Proceso B: 80%  × 30%
Proceso C: 40%  × 30%
Proceso D: 0%   × 20%

Avance = 52%
```

El porcentaje mostrado al usuario debe ser consistente con el workflow.
