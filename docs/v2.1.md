## 1. Principio rector: nada de listas fijas en el código

1. **Toda lista, etiqueta, umbral o parámetro vive en la base de datos** y se edita desde Settings.
2. **El código depende de *categorías semánticas* y de *permisos*, nunca de etiquetas ni de nombres de rol.** Ejemplo: la lógica de estancamiento no busca el estado "Espera de respuesta"; busca estados con categoría `WAITING`. El administrador puede renombrarlo, recolorearlo o crear otros.
3. **Los códigos son inmutables una vez usados; las etiquetas son editables.** Los registros no se borran: se **desactivan** con un toggle (`is_active`). Así ningún dato histórico queda huérfano.
4. **Desactivar nunca destruye datos.** Los casos, documentos y auditoría existentes conservan lo que usaron.
5. **Todo cambio de configuración se audita** (quién, cuándo, valor anterior, valor nuevo, motivo).

### 1.1 Qué es editable y qué está protegido

| Editable desde Settings | Protegido (lo define el código, por integridad) |
|---|---|
| Tipos de documento de identidad, tipos de persona | Tipos de movimiento de caja (`INCOME`, `EXPENSE`, `ADJUSTMENT`, `REVERSAL`) |
| Roles ("tipos de personal") y sus permisos | Códigos de permiso (el administrador **compone** roles con ellos, no inventa permisos nuevos) |
| Prioridades, estados de caso y de proceso (etiqueta, color, %) | Categorías semánticas (`DONE`, `WAITING`, etc.) que usa la lógica |
| Frecuencias de recurrencia, categorías de caja, monedas, países | Estados técnicos (trabajos, generación de documentos) y tipos de evento de auditoría |
| Campos personalizados ("variables") de clientes y casos | Operadores y hechos base del motor de reglas (los campos personalizados se agregan solos como hechos) |
| Módulos y funciones (toggles), parámetros, alertas, apariencia | Rol `ADMIN` (superusuario), auditoría, RLS y validación de archivos (no se pueden apagar) |

## 3. Modelo de datos de configuración

### 3.1 Catálogos genéricos

Un solo mecanismo para todas las listas editables.

```sql
create table catalogs (
  code            text primary key,            -- 'identity_document_types'
  name            text not null,
  description     text,
  module          text not null,               -- 'clients', 'cases', 'cash', ...
  allow_new_items boolean not null default true,
  item_schema     jsonb not null default '{}', -- JSON Schema que valida catalog_items.metadata
  is_system       boolean not null default false
);

create table catalog_items (
  catalog_code text not null references catalogs(code),
  code         text not null,                  -- inmutable una vez usado
  label        text not null,                  -- editable
  description  text,
  sort_order   int  not null default 0,
  color        text,                           -- token semántico, no hex libre
  metadata     jsonb not null default '{}',    -- validado contra item_schema
  is_system    boolean not null default false, -- protegido: no se elimina ni cambia su code
  is_active    boolean not null default true,  -- TOGGLE
  created_at   timestamptz not null default now(),
  updated_at   timestamptz not null default now(),
  primary key (catalog_code, code)
);
```

**Referencias desde las tablas de negocio**: se guarda el `code` legible con clave foránea compuesta, de modo que la integridad se garantiza y desactivar un elemento nunca rompe registros antiguos.

```sql
alter table clients
  add column person_type      text not null,
  add column person_type_cat  text generated always as ('person_types') stored,
  add foreign key (person_type_cat, person_type) references catalog_items (catalog_code, code);
-- Verificar en la migración; alternativa equivalente: trigger private.assert_catalog_item(...)
```

Un trigger adicional impide **asignar** un elemento inactivo en registros nuevos o modificados (los registros existentes lo conservan).

### 3.3 Tipos de persona y documentos de identidad

`clients` reemplaza `client_type` (`PERSON`/`COMPANY`/`OTHER`) por `person_type` (catálogo) y `document_type` pasa a ser `identity_document_type` (catálogo). Además se agregan `second_last_name` (apellido materno, que devuelven las consultas de DNI) y `custom_data jsonb`.

Ejemplo de `metadata` de un documento de identidad (todo editable):

```json
{
  "person_types": ["NATURAL"],
  "min_length": 8,
  "max_length": 8,
  "pattern": "^\\d{8}$",
  "check_algorithm": "NONE",
  "lookup_kind": "dni",
  "mask_visible_last": 3
}
```

| Documento | Patrón inicial | Comentario |
|---|---|---|
| `DNI` | `^\d{8}$` | Consulta automática habilitada |
| `RUC` | `^\d{11}$` + `check_algorithm: RUC_MOD11` | Aplica a persona jurídica y a persona natural con negocio |
| `CE` | `^[A-Za-z0-9]{9,12}$` | **Patrón provisional y permisivo: ajustarlo al formato vigente** desde Settings |
| `PASAPORTE` | `^[A-Za-z0-9]{6,12}$` | Inactivo por defecto (toggle) |

El formulario de cliente **se construye a partir de estos catálogos**: al elegir el tipo de persona se muestran los campos que corresponden (`PERSON` → nombres y apellidos; `COMPANY` → razón social y nombre comercial) y solo los documentos permitidos y activos. La validación (longitud, patrón, dígito verificador) se ejecuta con la misma función en el navegador, la API y un `CHECK`/trigger en la base de datos.

### 3.4 Campos personalizados ("variables")

Permite agregar datos nuevos a clientes, casos o procesos **sin tocar código ni hacer migraciones**.

```sql
create table custom_field_definitions (
  id             uuid primary key default gen_random_uuid(),
  entity         text not null check (entity in ('client','case','case_process')),
  code           text not null,                  -- clave dentro de custom_data; inmutable
  label          text not null,
  help_text      text,
  data_type      text not null check (data_type in
                  ('TEXT','TEXTAREA','NUMBER','DATE','BOOLEAN','CURRENCY','SELECT','MULTISELECT')),
  catalog_code   text references catalogs(code), -- opciones desde un catálogo
  options        jsonb,                          -- o lista de opciones inline
  is_required    boolean not null default false,
  validation     jsonb not null default '{}',    -- min, max, pattern, longitud
  default_value  jsonb,
  section        text,
  sort_order     int not null default 0,
  applies_to     jsonb not null default '{}',    -- visibilidad condicional: {"case_model_codes":[...],"person_types":[...]}
  read_permission  text,                         -- permiso opcional para ver
  write_permission text,                         -- permiso opcional para editar
  is_active      boolean not null default true,  -- TOGGLE
  is_system      boolean not null default false,
  unique (entity, code)
);
```

- Los valores se guardan en `custom_data jsonb` de la entidad (`clients`, `cases`, `case_processes`).
- **Validación**: una función única (`validate_custom_data(entity, data)`) construye el esquema desde las definiciones activas y se ejecuta en el `engine`/RPC y en un trigger liviano de la base de datos (requeridos y tipos).
- **Se integran solas** con el resto del sistema: aparecen como hechos del motor de reglas (`client.custom_data.<code>`, `case.custom_data.<code>`), como origen en `document_fields.source_path` y como columnas/filtros opcionales en listados.
- **Desactivar** oculta el campo y deja de exigirlo, pero **conserva los valores**. Si una plantilla lo usa como obligatorio, el sistema advierte y bloquea la desactivación hasta corregir la plantilla.
- **No se cambia el `data_type` de un campo con valores**: se crea uno nuevo.

**Cómo se hace cumplir un toggle (tres capas, no solo la interfaz):**

1. **UI**: el módulo apagado no aparece en el menú ni en las rutas.
2. **API/engine**: responde `403 feature_disabled`.
3. **Base de datos**: las políticas RLS y las funciones verifican el flag, de modo que un módulo apagado no se puede usar ni por API directa.

```sql
create or replace function private.feature_enabled(_key text) returns boolean
language sql stable security definer set search_path = '' as $$
  select coalesce((select is_enabled from public.feature_flags where key = _key), false);
$$;

-- Ejemplo: la caja solo es accesible si el módulo está activo Y el usuario tiene el permiso
create policy cash_movements_select on public.cash_movements for select to authenticated
  using ((select private.feature_enabled('module.cash'))
     and (select private.has_permission('cash.read')));
```

Reglas del panel de módulos: no se puede activar un flag si sus dependencias están apagadas o falta configuración requerida (el panel muestra qué falta); apagar un módulo **conserva sus datos** y pausa sus trabajos programados.

### 3.6 Toggles de procesos, estados, documentos y variables

Todo elemento configurable tiene `is_active`. Qué ocurre al desactivarlo:

| Elemento | Al desactivar |
|---|---|
| **Proceso** en un modelo | Los casos en curso lo conservan (tienen copia propia). En una versión de modelo `PUBLISHED` no se edita: el botón ofrece **"Crear nueva versión con este cambio"** |
| **Estado de workflow o de caso** | Se bloquea si algún caso/proceso abierto lo usa; se listan cuáles |
| **Tipo de documento / plantilla** | Los casos en curso conservan lo generado; deja de aparecer para casos nuevos. Una plantilla inactiva no genera |
| **Regla documental** | Deja de aplicar desde ese momento. El panel invita a correr el simulador antes de confirmar |
| **Campo personalizado / campo de documento** | Se oculta y no se exige; los valores se conservan (ver 3.4) |
| **Elemento de catálogo** | No aparece en formularios nuevos; los registros existentes lo conservan. No se puede desactivar el valor por defecto ni el único activo de un catálogo obligatorio |
| **Rol** | Se avisa cuántos usuarios quedarían sin acceso |
| **Módulo / función** | Ver 3.5 |

Patrón de interfaz: interruptor (*toggle*) con etiqueta **"En uso (N)"**; al desactivar, un diálogo muestra el impacto antes de confirmar; los elementos `is_system` muestran un candado y no permiten eliminar ni cambiar su código.

### 3.8 Roles ("tipos de personal") y permisos editables

Para que el administrador pueda crear roles nuevos (Supervisor, Legal, Asistente…) sin tocar código, **la RLS deja de preguntar por el nombre del rol y pregunta por permisos**. Esto reemplaza las funciones `has_role('ADMIN')` de v2.0 §5.2.

```sql
alter table roles
  add column is_system    boolean not null default false,   -- ADMIN, ANALYST, CONSULT, CASHIER
  add column is_superuser boolean not null default false;   -- ADMIN: todos los permisos

create or replace function private.has_permission(_perm text) returns boolean
language sql stable security definer set search_path = '' as $$
  select exists (
    select 1
      from public.user_roles ur
      join public.roles r on r.id = ur.role_id and r.is_active
      left join public.role_permissions rp on rp.role_id = r.id
      left join public.permissions p on p.id = rp.permission_id
     where ur.user_id = (select auth.uid())
       and (r.is_superuser or p.code = _perm));
$$;

create or replace function private.can_access_case(_case_id uuid) returns boolean
language sql stable security definer set search_path = '' as $$
  select private.has_permission('cases.read.all')
      or (private.has_permission('cases.read.assigned')
          and exists (select 1 from public.case_assignments ca
                       where ca.case_id = _case_id
                         and ca.user_id = (select auth.uid())
                         and ca.ended_at is null));
$$;
```

**Catálogo de permisos** (definido por el código; el administrador solo los asigna a roles):

| Módulo | Permisos |
|---|---|
| Clientes | `clients.read`, `clients.write` |
| Casos | `cases.read.all`, `cases.read.assigned`, `cases.create`, `cases.write.all`, `cases.write.assigned`, `cases.close` |
| Procesos | `processes.update` |
| Documentos | `documents.read`, `documents.upload`, `documents.generate`, `documents.approve` |
| Configuración documental | `templates.manage`, `rules.manage`, `models.manage` |
| IA | `ai.use`, `ai.manage` |
| Cotizaciones | `quotes.read`, `quotes.write` |
| Caja | `cash.read`, `cash.write`, `cash.request`, `cash.approve`, `cash.close` |
| Reportes | `reports.read`, `reports.export` |
| Administración | `users.manage`, `roles.manage`, `settings.manage`, `audit.read`, `monitoring.read` |

**Protecciones**: `ADMIN` es superusuario y no se puede editar ni desactivar; un trigger impide desactivar o quitar el rol al **último administrador activo**; los roles semilla (`ANALYST`, `CONSULT`, `CASHIER`) pueden renombrarse y ajustar sus permisos, pero no eliminarse. Un usuario puede tener varios roles (los permisos se suman).

### 3.9 Auditoría de configuración y portabilidad

- Todo cambio en `system_settings`, `feature_flags`, catálogos, campos personalizados, roles y permisos se registra en `settings_history`/`audit_logs` (append-only).
- **Exportar/importar configuración** (Settings → Avanzado): un JSON versionado con catálogos, flags, parámetros, roles y permisos, campos personalizados y estados. La importación muestra un *diff* previo y permite **promover la configuración de staging a producción** sin recapturarla.
- **Restaurar valores por defecto** por pestaña, con confirmación.

## 4. Consulta de DNI/RUC con APIINTI

### 4.1 Diseño

```text
Formulario de cliente ─► engine (Render) ─► IdentityLookupProvider ─► APIINTI
                              │
                              ├─ caché (identity_lookup_cache)
                              └─ auditoría (IDENTITY_LOOKUP)
```

- **El navegador nunca llama a APIINTI**: la clave viviría expuesta. Toda consulta pasa por `POST /v1/integrations/identity/lookup` del engine.
- Interfaz `IdentityLookupProvider.lookup(kind, number)` que devuelve un formato interno normalizado: `document_number`, `person_type`, `first_name`, `last_name`, `second_last_name`, `legal_name`, `trade_name`, `address`, `status`, `condition`. Cambiar de proveedor implica escribir otro adaptador, no tocar el negocio.
- Endpoint base, tiempo de espera y **mapeo de campos** de la respuesta son configurables (`integrations.identity_lookup.*`), para absorber cambios del proveedor sin desplegar código.
- **Caché** en `identity_lookup_cache (doc_type, number, payload, fetched_at, expires_at)`, con vigencia configurable (`clients.lookup_cache_days`), acceso solo para el engine y limpieza periódica. Reduce consumo de cuota y datos personales almacenados.
- **Cuota**: contador mensual de consultas y aviso al llegar al 80 % de `identity_lookup.monthly_quota` (el límite lo ingresa el administrador, según su plan en APIINTI).
- **Resiliencia**: la consulta es una ayuda, **nunca bloquea** el alta manual del cliente. Si falla o no hay cuota, el formulario permite completar los datos a mano.
- **Trazabilidad**: cada consulta registra usuario, fecha y tipo de documento (número enmascarado) y finalidad "alta/actualización de cliente".
- Tratamiento de datos personales: el DNI es dato personal; consultarlo requiere una finalidad legítima y su tratamiento debe alinearse con la Ley 29733 (revisar con asesoría legal).

> **Documentación pendiente:** no pude acceder a la documentación pública de APIINTI. Antes de la Fase 5, guarda en `docs/integrations/apiinti.md` (copiando desde tu dashboard) la URL base, la forma de autenticación, los endpoints de DNI y RUC y un ejemplo de respuesta. El adaptador se escribe a partir de ese archivo.

### 4.2 ⚠️ Sobre la API key compartida

La clave se pegó en texto claro en esta conversación, por lo que **debe considerarse expuesta**:

1. **Regenérala** en el panel de APIINTI cuando puedas (y de todas formas antes de producción).
2. Guárdala **solo** como variable de entorno `APIINTI_API_KEY` en Render (y en un `.env` local ignorado por git).
3. **Nunca** en el repositorio, en `system_settings`, en el frontend ni en prompts a Antigravity (los agentes pueden copiarla a archivos o commits).
4. El repositorio incluye un `.env.example` solo con nombres de variables y valores vacíos, y el CI ejecuta un escáner de secretos.

## 5. Operación en plan gratuito

*Verificado con documentación pública el 23-sep-2026; los límites cambian con frecuencia, confirmarlos antes de depender de ellos.*

| Servicio | Limitación relevante | Adaptación en el diseño |
|---|---|---|
| **Supabase Free** | Pausa proyectos con poca actividad (~1 semana); **sin backups**; 2 proyectos activos; ~500 MB de base de datos y ~1 GB de archivos | Staging y producción ocupan los 2 proyectos (el desarrollo es local con Docker). **Backup propio**: un workflow de GitHub Actions ejecuta `pg_dump` cifrado y exporta Storage a un almacenamiento privado. Límite de archivo reducido (`documents.max_file_mb`) y alerta de uso de espacio |
| **Render Free** | Se duerme a los 15 min sin tráfico y tarda ~1 min en despertar; 750 h/mes; filesystem efímero; **sin worker ni cron persistentes** (son de pago) | Modo **`jobs_mode = TICK`**: `pg_cron` (Supabase) llama por HTTP (`pg_net`) a `POST /v1/jobs/tick` del engine cada 30 min y a las horas clave (07:30 y 23:00 Lima). El servicio despierta, procesa la cola y vuelve a dormir. La interfaz muestra "Despertando el servicio…" en la primera generación |
| **Vercel Hobby** | Pensado para uso personal/no comercial según sus términos; cron limitado a 1 vez al día | Válido para desarrollo y piloto interno; **revisar sus términos antes del uso comercial**. No se usa Vercel Cron |
| **IA** | Requiere clave de un proveedor (con cuota gratuita limitada o de pago) | `module.ai` apagado hasta decidir D3 |
| **Telegram** | Bot API gratuita | Sin cambios |

**Consecuencias que se aceptan al usar plan gratuito**

- Las alertas no son instantáneas: llegan en el siguiente *tick* (hasta ~30 min de retraso). Se documenta en la pantalla de alertas.
- **No se mantiene el servicio despierto con pings artificiales.** Render señala en su comunidad que hacerlo va contra el espíritu del plan gratuito. Por eso, en modo `TICK` el monitor externo vigila Vercel y Supabase, y el estado de Render se comprueba en cada *tick*.
- **LibreOffice con poca memoria**: la instancia gratuita de Render es pequeña (unos 512 MB según su documentación; verificar). La conversión a PDF puede ser lenta o fallar. Por eso `docs.pdf_generation` es un toggle: se prueba en staging y, si no es estable, se opera solo con Word hasta pasar a un plan de pago.
- **Los jobs de v2.0 §10 siguen igual en producción de pago**; solo cambia el modo de ejecución (`CONTINUOUS`).

```sql
-- Modo TICK: pg_cron despierta al engine (el secreto va en Supabase Vault, no en el SQL)
select cron.schedule('engine_tick', '*/30 * * * *', $$
  select net.http_post(
    url     := '<URL_DEL_ENGINE>/v1/jobs/tick',
    headers := jsonb_build_object('Authorization', 'Bearer ' || '<SECRETO_DESDE_VAULT>')
  ) $$);
```

**Recomendación honesta:** el plan gratuito es adecuado para **desarrollar y hacer el piloto con datos de prueba**. Antes de cargar **datos reales de clientes** (documentos jurídicos, DNI, caja chica), sube al menos **Supabase a Pro** (backups diarios y sin pausas); Render y Vercel pueden esperar más. Cambiar de plan no requiere cambios de código: basta pasar `platform.tier` a `PAID` y `platform.jobs_mode` a `CONTINUOUS`.
