## 1. Evaluación del proyecto

### 1.1 Fortalezas (se mantienen)

- **Principio "reglas + IA + control humano"**: la IA solo recomienda y explica; las reglas de negocio mandan. Es la decisión más importante del proyecto y es correcta.
- **Cadena documental clara**: CaseModel → Process → DocumentType → Template → DocumentRule → Recomendación → Documento generado.
- **Configurabilidad sin código**: modelos, procesos, estados, pesos y reglas administrables.
- **Trazabilidad**: versionado, auditoría, evidencia de cada recomendación.
- **Seguridad en base de datos (RLS)**, no solo en la interfaz.
- **Roadmap por fases** con el generador documental antes que la IA (la IA necesita historial para aprender; al inicio no lo hay).

### 1.2 Riesgos principales

| # | Riesgo | Impacto | Mitigación en v2 |
|---|---|---|---|
| R1 | Alcance muy amplio (workflow + documentos + IA + caja + monitoreo + reportes) | Retrasos, calidad dispareja | MVP definido en la sección 13 (Casos + Workflow + Documentos + Generación con reglas, sin IA) |
| R2 | El motor Word/PDF asignado a Edge Functions (v1 §52) no es viable | Bloqueo técnico a mitad de proyecto | Servicio Docker en Render con LibreOffice (sección 8) |
| R3 | Datos personales y jurídicos enviados a un LLM externo | Riesgo legal y de confidencialidad | Minimización, enmascarado, modo "solo reglas", revisión legal (sección 7.6) |
| R4 | Caja chica con saldo mutable y sin cierre de periodos | Descuadres, fraude, no auditable | Libro contable inmutable con reversos y periodos cerrados (sección 9) |
| R5 | Tres proveedores (Vercel, Render, Supabase) con planes gratuitos que se pausan o duermen | Caídas y pérdida de datos en producción | Planes mínimos de producción (sección 2.3) |
| R6 | Reglas documentales con dos sintaxis distintas y sin simulador | Recomendaciones incorrectas e imposibles de depurar | DSL único + simulador (sección 6) |
| R7 | Cambiar un modelo de caso altera casos en curso | Inconsistencias entre casos abiertos | Versiones de modelo publicadas e inmutables (sección 4) |
| R8 | RLS mal diseñada (recursión, lentitud, huecos) | Fuga de datos o lentitud | Funciones auxiliares en esquema `private`, pruebas automáticas de RLS (secciones 5 y 12) |

## 2. Arquitectura y despliegue

### 2.1 Diagrama

```text
                Navegador (móvil / tablet / escritorio)
                               │
                               ▼
                ┌──────────────────────────────┐
                │ VERCEL — Next.js (apps/web)  │  UI + SSR + sesión
                └───────┬──────────────┬───────┘
     CRUD con JWT       │              │  operaciones privilegiadas (JWT del usuario)
     del usuario (RLS)  │              ▼
                        │     ┌───────────────────────────────┐
                        │     │ RENDER — engine (Docker)      │
                        │     │ · Render DOCX + PDF           │
                        │     │ · Orquestación IA             │
                        │     │ · DNI/RUC, Telegram (webhook) │
                        │     │ · Worker de job_queue         │
                        │     └───────┬───────────────────────┘
                        ▼             ▼
                ┌──────────────────────────────┐
                │ SUPABASE                     │
                │ Postgres + RLS · Auth · MFA  │
                │ Storage privado · Realtime   │
                │ pg_cron · pg_net · pgvector  │
                └──────────────────────────────┘
```

### 2.2 Responsabilidades

| Componente | Hace | No hace |
|---|---|---|
| **Vercel (Next.js)** | UI, SSR, sesión (`@supabase/ssr`), CRUD contra Supabase con el JWT del usuario (RLS aplica) | Guardar `service_role`; procesar DOCX/PDF; llamar directamente a un LLM |
| **Supabase** | Datos, RLS, Auth, MFA, Storage privado, Realtime, `pg_cron`/`pg_net`, pgvector | Lógica pesada. Las Edge Functions se usan solo para hooks livianos (p. ej. Auth Hook), no como backend principal |
| **Render — `engine`** | Generación DOCX/PDF, orquestación IA, integraciones DNI/RUC, webhook de Telegram, health checks, worker de `job_queue` | Servir la interfaz |

**Decisión:** un solo servicio Render al inicio (HTTP + loop de worker en el mismo proceso). Se separa en `engine` y `worker` solo si la carga lo exige. Un único "backend de confianza" evita duplicar lógica entre Edge Functions y Render.

**Cadena de confianza:** el navegador llama a Vercel con su sesión. Cuando se requiere una operación privilegiada, Next.js llama a Render enviando el JWT del usuario. Render lo valida con las claves de firma de Supabase (JWKS) y **lee los datos con un cliente que usa ese JWT**, de modo que RLS sigue aplicando. La `service_role` se usa en Render solo para escribir en Storage, actualizar el estado de trabajos y registrar auditoría.

- Tres entornos: **local** (Supabase CLI + Docker), **staging** y **producción**, cada uno con su proyecto Supabase, variables de entorno y servicio Render propios.

## 4. Modelo de datos — cambios sobre v1

### 4.1 Convenciones adicionales

- **ENUMs de PostgreSQL o `CHECK`** en lugar de `TEXT` libre para estados y tipos.
- **Todas las FK con índice** (PostgreSQL no los crea automáticamente).
- Trigger `set_updated_at` en todas las tablas con `updated_at`.
- `case_number` con formato `AAAA-NNNNNN` mediante contador anual seguro ante concurrencia (SQL abajo).
- Montos: `numeric(14,2)`. Fechas: `timestamptz` en UTC; presentación en `America/Lima`.
- Índices parciales para registros activos y `GIN` solo en columnas `jsonb` realmente consultadas.
- `clients`: `UNIQUE(document_type, document_number)` con validación de formato (DNI 8 dígitos, RUC 11 dígitos con dígito verificador).
- `quotes`: índice único parcial que permite **una sola** cotización `is_selected` por caso.
- `templates`: restricción de exclusión para que no existan dos plantillas activas con vigencias solapadas para el mismo tipo documental.

**Número de caso seguro ante concurrencia**

```sql
create table case_counters (year int primary key, last_value int not null default 0);

create or replace function public.next_case_number() returns text
language plpgsql as $$
declare
  y int := extract(year from (now() at time zone 'America/Lima'));
  n int;
begin
  insert into case_counters(year, last_value) values (y, 1)
  on conflict (year) do update set last_value = case_counters.last_value + 1
  returning last_value into n;
  return y || '-' || lpad(n::text, 6, '0');
end $$;
```

**Avance: el porcentaje del proceso sale del estado (o de un override manual) y el del caso se recalcula por trigger**

```sql
create or replace function private.tg_case_process_progress() returns trigger
language plpgsql security definer set search_path = '' as $$
declare
  v_prev numeric := 0;
  v_case uuid;
begin
  if tg_when = 'BEFORE' then
    if tg_op = 'UPDATE' then v_prev := coalesce(old.progress, 0); end if;
    new.progress := coalesce(
      new.manual_progress,
      (select case when ws.keeps_previous_progress then v_prev else ws.percentage end
         from public.workflow_statuses ws where ws.id = new.status_id),
      0);
    return new;
  end if;

  -- AFTER: recalcular el avance del caso
  if tg_op = 'DELETE' then v_case := old.case_id; else v_case := new.case_id; end if;
  update public.cases c
     set current_progress = coalesce((
           select round(sum(cp.progress * cp.weight) / nullif(sum(cp.weight), 0), 2)
             from public.case_processes cp
            where cp.case_id = c.id and cp.is_applicable), 0),
         updated_at = now()
   where c.id = v_case;
  return null;
end $$;

-- Un trigger BEFORE (insert/update) y otro AFTER (insert/update/delete) sobre case_processes.
-- Prueba unitaria obligatoria: pesos 20/30/30/20 con avances 100/80/40/0 => 56.00
```

**Libro de caja inmutable (correcciones mediante reverso, nunca UPDATE/DELETE)**

```sql

  id              uuid primary key default gen_random_uuid(),
  cash_account_id uuid not null references cash_accounts(id),
  direction       cash_direction not null,
  amount          numeric(14,2) not null check (amount > 0),
  movement_kind   text not null check (movement_kind in ('INCOME','EXPENSE','ADJUSTMENT','REVERSAL')),
  reversal_of     uuid references cash_movements(id),

begin raise exception 'Registro inmutable: use un movimiento de reverso'; end $$;

  before update or delete on cash_movements
  for each row execute function private.raise_immutable();

begin
  if exists (select 1 from public.cash_periods p
              where p.cash_account_id = new.cash_account_id
                and p.status = 'CLOSED'
                and new.movement_date between p.period_start and p.period_end) then
    raise exception 'Periodo cerrado: registre el movimiento en el periodo vigente';
  end if;
  return new;
end $$;
create trigger cash_movements_period_guard
  before insert on cash_movements
  for each row execute function private.tg_cash_period_guard();

create view cash_account_balances with (security_invoker = true) as
select a.id as cash_account_id,
       a.opening_balance
         + coalesce(sum(case m.direction when 'IN' then m.amount else -m.amount end), 0) as balance
from cash_accounts a
left join cash_movements m on m.cash_account_id = a.id
group by a.id, a.opening_balance;

-- Control dual: quien abre el arqueo no lo aprueba
alter table cash_reconciliations
  add constraint reconciliation_dual_control check (approved_by is null or approved_by <> opened_by);
```

**Auditoría append-only** (misma técnica: `revoke update, delete` + trigger `raise_immutable` sobre `audit_logs`). La IP y el user agent se registran desde la capa API, no desde triggers.

### 5.2 Funciones auxiliares y políticas

> **v2.1:** las políticas de este ejemplo usan `has_role(...)` solo como ilustración. En la implementación se usan `private.has_permission(...)` y `private.feature_enabled(...)` (anexo v2.1 §3.5 y §3.8), para que los roles sean editables.

Las funciones viven en el esquema `private` (no expuesto por la API), son `SECURITY DEFINER` con `search_path` vacío, y en las políticas se invocan envueltas en `(select ...)` para que PostgreSQL las evalúe una sola vez por consulta. Esto evita recursión entre políticas y mejora el rendimiento.

```sql
create schema if not exists private;
grant usage on schema private to authenticated;

create or replace function private.has_role(_role text) returns boolean
language sql stable security definer set search_path = '' as $$
  select exists (
    select 1 from public.user_roles ur
    join public.roles r on r.id = ur.role_id
    where ur.user_id = (select auth.uid()) and r.code = _role and r.is_active);
$$;

create or replace function private.can_access_case(_case_id uuid) returns boolean
language sql stable security definer set search_path = '' as $$
  select private.has_role('ADMIN')
      or exists (select 1 from public.case_assignments ca
                 where ca.case_id = _case_id
                   and ca.user_id = (select auth.uid())
                   and ca.ended_at is null);
$$;

revoke execute on function private.has_role(text), private.can_access_case(uuid) from public, anon;
grant  execute on function private.has_role(text), private.can_access_case(uuid) to authenticated;

alter table public.cases enable row level security;

create policy cases_select on public.cases for select to authenticated
  using ((select private.can_access_case(id)));

create policy cases_insert on public.cases for insert to authenticated
  with check ((select private.has_role('ADMIN')) or (select private.has_role('ANALYST')));

-- cases_update / cases_delete: private.can_write_case(id) = ADMIN, o ANALYST asignado (no VIEWER)

-- Caja: MFA obligatorio (nivel de aseguramiento aal2) para escribir
create policy cash_movements_insert on public.cash_movements for insert to authenticated
  with check ((select private.has_role('CASHIER')) and (select auth.jwt() ->> 'aal') = 'aal2');
```

Regla general: **toda tabla hija de `cases` reutiliza `can_access_case(case_id)`**, de modo que la visibilidad se define en un solo lugar.

### 5.4 Controles adicionales

- **RLS activada en toda tabla de `public`**; una prueba de CI falla si existe una tabla sin RLS (`pg_class.relrowsecurity = false`). Las vistas usan `security_invoker = true`.
- **`service_role` nunca en el navegador** ni en variables `NEXT_PUBLIC_*`. Secretos solo en variables de entorno de Vercel y Render, distintos por entorno y con rotación.
- **MFA (TOTP) obligatorio** para ADMIN y CASHIER; recomendado para ANALYST. Expiración de sesión por inactividad.
- **Subida de archivos**: lista blanca de MIME + verificación de firma de archivo (magic bytes), tamaño máximo configurable (25 MB por defecto), rechazo de macros (`.docm`, `vbaProject.bin`), nombres saneados. Antivirus (ClamAV en Render) como mejora posterior.
- **Cabeceras**: CSP estricta, HSTS, `frame-ancestors 'none'`. **Rate limiting** por usuario en endpoints de IA y generación.
- **Datos personales**: enmascarar documento de identidad en listados (mostrar completo solo con permiso); política de retención para `clients.external_data`.
- **Auditoría**: append-only; incluye lecturas sensibles y descargas registradas desde la capa API (IP y user agent incluidos).

## 6. Motor de reglas documentales (DSL único)

Reemplaza las dos sintaxis de v1 (§5.1 y §13). Se evalúa con **funciones puras** en `packages/shared/rules` (sin acceso a la BD): el `engine` arma el contexto y la función devuelve resultado + traza.

```json
{
  "version": 1,
  "conditions": {
    "all": [
      { "fact": "client.client_type", "op": "eq", "value": "COMPANY" },
      { "fact": "case_model.code",    "op": "eq", "value": "CONSTITUCION" },
      { "fact": "process.code",       "op": "eq", "value": "MINUTA" },
      { "any": [
          { "fact": "case.custom_data.capital", "op": "gte", "value": 10000 },
          { "fact": "docs.types", "op": "contains", "value": "PODER_REPRESENTANTE" }
      ]},
      { "not": { "fact": "docs.types", "op": "contains", "value": "MINUTA" } }
    ]
  },
  "effect": { "type": "RECOMMEND", "priority": 1 },
  "explanation": "Constitución de empresa: la minuta es requerida en este proceso"
}
```

| Elemento | Definición |
|---|---|
| **Combinadores** | `all`, `any`, `not` (anidables) |
| **Operadores** | `eq`, `neq`, `in`, `not_in`, `gt`, `gte`, `lt`, `lte`, `between`, `contains`, `exists`, `missing`, `starts_with` |
| **Hechos permitidos (whitelist)** | `client.client_type`, `client.country`, `client.document_type`, `case_model.code`, `case.priority`, `case.age_days`, `case.custom_data.<clave>`, `process.code`, `process.status_code`, `docs.types`, `docs.approved_types`, `quote.selected_amount` |
| **Efectos** | `RECOMMEND` (sugerir), `EXCLUDE` (descartar), `REQUIRE` (marcar obligatorio) |
| **Resolución** | Se evalúan todas las reglas activas; `EXCLUDE` gana sobre `RECOMMEND` de igual o menor prioridad (número mayor); `REQUIRE` se acumula; el orden final sale de `priority` |

Reglas de implementación:

1. **Sin `eval` ni expresiones libres.** Al guardar, un esquema zod rechaza hechos u operadores fuera de la whitelist.
2. La evaluación devuelve una **traza** (`rule_id`, coincidió sí/no, valores usados, efecto) que se guarda en `ai_recommendations.rules_triggered`.
3. Las reglas pertenecen a una versión de modelo; cambiarlas implica una nueva versión.
4. **Simulador (M7)**: pantalla de administración que ejecuta el motor sobre un caso real y muestra qué reglas aplican y por qué.
5. Pruebas por tabla: mínimo 40 casos (cada operador, anidamiento, valores nulos, conflictos de prioridad).

## 7. IA documental

### 7.1 Pipeline (las reglas van primero, la IA elige entre candidatos)

```text
1. Contexto     → CaseContext mínimo, con campos en lista blanca
2. Reglas       → conjunto cerrado de candidatos C (tipos + plantillas vigentes)
3. Historial    → estadística SQL: cuántas veces se aceptó cada candidato en casos similares
4. Conocimiento → top-k fragmentos de knowledge_chunks (pgvector), si aplica
5. IA           → ordena SOLO los candidatos de C y redacta explicación y campos faltantes
6. Validación   → zod: todo código/plantilla ∈ C; si no, se descarta; máximo 1 reintento
7. Resultado    → ai_recommendations (con traza completa)
```

**La IA no puede inventar documentos**: si devuelve algo fuera de C, se ignora.

### 7.2 Contrato de salida (validado con zod)

```json
{
  "recommended": { "document_type_code": "INFORME_PROVEEDORES", "template_id": "uuid", "reasons": ["..."] },
  "alternatives": [ { "document_type_code": "CONTRATO_SERVICIOS", "template_id": "uuid", "why": "..." } ],
  "missing_fields": ["proveedor", "monto"],
  "prefill": [ { "field_code": "descripcion", "value": "...", "source": "case.description" } ],
  "similar_cases": ["2026-000412"]
}
```

### 7.3 Puntuación, no "confianza" autodeclarada

Un LLM no calibra su propia confianza. La puntuación se calcula en el sistema:

```text
score = w1 · prioridad_de_regla + w2 · tasa_histórica_de_aceptación + w3 · completitud_de_datos
tasa_histórica = (aceptadas + 1) / (mostradas + 2)      # suavizado de Laplace
```

Pesos iniciales (0.5 / 0.3 / 0.2) y umbrales (Alta ≥ 0.75, Media ≥ 0.50) en `system_settings.ai`; se recalibran con datos reales.

### 7.4 Prellenado

Los valores conocidos salen **determinísticamente de la BD**. La IA solo propone texto para campos narrativos, y cada valor propuesto declara su `source`. El usuario confirma antes de generar.

### 7.5 Degradación controlada

Si el proveedor falla o excede el timeout (20 s), el sistema responde en **modo solo reglas** (reglas + estadística histórica) marcando `model_provider = 'RULES_ONLY'`. El flujo nunca queda bloqueado por la IA.

### 7.6 Privacidad y cumplimiento

- Enviar únicamente los campos estrictamente necesarios (lista blanca por función).
- **Enmascarar** DNI, RUC, correo, teléfono y dirección con tokens (`[CLIENTE_1]`) y rehidratarlos localmente al recibir la respuesta.
- No enviar archivos completos. Resumir un documento requiere activación explícita del administrador y fragmentos mínimos.
- Proveedor con condiciones de **no entrenamiento** con datos del cliente y retención mínima o nula; registrar proveedor y región.
- Bandera `cases.ai_allowed` y modo global "solo reglas" (M10) para casos confidenciales.
- Guardar en `ai_recommendations.input_summary` **qué campos salieron** (no sus valores).
- La Ley 29733 de Protección de Datos Personales del Perú y su reglamento aplican al tratamiento de datos personales, y usar proveedores en el extranjero puede implicar flujo transfronterizo; además puede existir secreto profesional según el giro del negocio. **Validar con asesoría legal antes de producción.**

### 7.7 Seguridad frente a inyección de instrucciones

Los documentos subidos, la base de conocimiento y los textos de clientes se tratan como **datos, nunca como instrucciones**: van delimitados en el prompt, el modelo no tiene herramientas ni acceso de escritura, y su salida solo puede seleccionar candidatos ya autorizados por reglas.

### 7.8 Costos y proveedor

- `AiProvider` es una interfaz (`recommend`, `embed`); el proveedor y el modelo se configuran en `system_settings.ai`. La lógica de negocio no depende de un proveedor concreto.
- `ai_usage_log` por usuario y mes, presupuesto mensual con alerta al 80 %, límite de solicitudes por usuario y caché por `context_hash`.

### 7.9 "Aprender del historial" (v1 §36) — definición operativa

No hay *fine-tuning*. El aprendizaje es: (a) estadística de aceptación/rechazo, (b) recuperación de casos similares y (c) fragmentos de conocimiento aprobados por el administrador. Toda mejora pasa por revisión humana.

### 7.10 Evaluación

- Conjunto dorado de al menos 50 casos con respuesta esperada; métricas top-1 y top-3.
- Prueba de regresión obligatoria al cambiar `prompt_version` o el modelo.
- Pruebas de inyección (documento con instrucciones maliciosas no debe alterar el resultado).

## 8. Motor documental (Word/PDF)

### 8.1 Endpoints del `engine` (Render)

| Endpoint | Uso |
|---|---|
| `POST /v1/recommendations` | Ejecuta el pipeline de la sección 7 |
| `POST /v1/documents/preview` | PDF borrador con marca de agua "BORRADOR" |
| `POST /v1/generation-jobs` | Encola la generación final (idempotente por `idempotency_key`) |
| `GET /v1/downloads/:versionId` | Audita y redirige a URL firmada (60 s) |
| `POST /v1/integrations/{dni,ruc}/lookup` | Consulta con caché y adaptador de proveedor |
| `POST /v1/telegram/webhook` | Vinculación y comandos (con token secreto) |
| `GET /healthz`, `GET /readyz` | Salud del servicio |

### 8.2 Pipeline de generación (asíncrono)

1. El frontend crea un `generation_job` mediante una RPC (RLS valida permisos) y se suscribe a **Realtime** para ver el estado. Así una espera de arranque en frío o un timeout no rompen la generación.
2. El worker valida datos: los campos se resuelven desde `document_fields.source_path` (lista blanca). Si faltan obligatorios, el job falla con la lista exacta.
3. Guarda un **snapshot** de los datos de entrada, la versión de plantilla y la traza de reglas.
4. Renderiza el DOCX y lo convierte a PDF.
5. Sube ambos a Storage, calcula SHA-256, crea `document_versions` (versión + 1) y `generated_documents`, registra `case_events` y auditoría.
6. Cierra el job. Cualquier reintento con la misma `idempotency_key` devuelve el resultado ya creado (no duplica versiones).

### 8.3 Plantillas DOCX

- Sintaxis `{{campo}}`, con bucles y condicionales para tablas y secciones opcionales. Motor sugerido: **docxtemplater**; algunos de sus módulos (p. ej. imágenes) son de pago, por lo que se debe evaluar `docx-templates` (MIT) si se requieren. *Verificar licencias antes de decidir.*
- **Lint al subir**: extrae los marcadores, los compara con `template_fields` y reporta faltantes y sobrantes. Word suele partir un marcador en varios fragmentos de texto; el lint detecta marcadores rotos.
- Rechazar `.docm` y cualquier archivo con macros. Usar estilos de Word (no formato manual) para que el resultado sea estable.
- **Fuentes**: instalar en la imagen Docker fuentes métricamente compatibles (por ejemplo Carlito para Calibri y Liberation para Arial/Times) y las fuentes corporativas con licencia. Sin esto, el PDF cambia saltos de línea y paginación respecto al Word.
- Cada plantilla activa tiene un **caso dorado** de prueba (datos de ejemplo + PDF de referencia) que se regenera en CI.

### 8.4 Conversión a PDF

LibreOffice headless con perfil aislado por trabajo (`-env:UserInstallation=file:///tmp/lo-<jobId>`), concurrencia limitada, tiempo máximo de 60 s y limpieza de procesos colgados. Alternativa equivalente: contenedor **Gotenberg** si se prefiere no administrar LibreOffice directamente.

### 8.5 Estados y aprobación

`QUEUED → GENERATING → GENERATED → IN_REVIEW → APPROVED | REJECTED`, más `FAILED` y `SUPERSEDED`.

- Solo `APPROVED` puede marcarse como final.
- Regenerar deja la versión anterior como `SUPERSEDED`; **nunca se sobrescribe**.
- Con `system_settings.documents.four_eyes = true`, quien aprueba debe ser distinto de quien generó.
- Errores con mensaje accionable y botón "Reintentar"; 3 reintentos automáticos con backoff.

## 9. Caja chica

- **Libro inmutable**: los errores se corrigen con un movimiento `REVERSAL` que apunta al original. El saldo es siempre `apertura + Σ movimientos` (vista `cash_account_balances`).
- **Flujo de solicitud** (resuelve "Solicitudes pendientes"): ANALYST crea `cash_request` (opcionalmente ligada a un caso) → ADMIN aprueba → CASHIER desembolsa (movimiento OUT con `request_id`) → rendición con soporte → cierre de la solicitud.
- **Cierre de periodo = arqueo**: se compara saldo del sistema vs. contado. Si hay diferencia se exige observación y aprobación de ADMIN; al aprobar, el periodo pasa a `CLOSED` y no admite movimientos retroactivos.
- **Controles**: MFA (`aal2`), control dual (quien abre el arqueo no lo aprueba), soporte obligatorio sobre un monto configurable, límite por movimiento que exige aprobación, alerta de saldo mínimo.
- **Aislamiento**: CASHIER no accede a casos ni documentos jurídicos. La IA nunca modifica saldos (v1 §36).
- **Monedas**: una moneda por cuenta; sin conversión en el MVP.
- **Reportes**: por categoría, por caso, por periodo y conciliaciones.
- **Pruebas**: propiedad "saldo de la vista = apertura + Σ movimientos" con pruebas aleatorias de reversos; intentos de `UPDATE`/`DELETE` deben fallar incluso con `service_role`.

## 10. Automatizaciones y alertas

**Mecanismo:** `pg_cron` (Supabase) inserta trabajos en `job_queue` con `dedupe_key`; el worker de Render los consume. Los trabajos sobreviven a reinicios y **no dependen de Vercel Cron**. `pg_cron` opera en UTC; Lima es UTC−5 sin horario de verano, por lo que las conversiones son fijas.

```sql
select cron.schedule('nightly_maintenance', '0 4 * * *', $$
  insert into public.job_queue (job_type, dedupe_key)
  values ('nightly_maintenance', 'nightly:' || current_date)
  on conflict (dedupe_key) do nothing $$);
```

| Trabajo | Hora Lima | Cron (UTC) | Acción |
|---|---|---|---|
| `health_checks` | cada 5 min | `*/5 * * * *` | Comprobar servicios y guardar en `service_health_checks` |
| `due_alerts` | cada hora (respeta `working_hours`) | `0 * * * *` | Alertas T-3, T-1, día D y vencidos |
| `recurrence_create` | 06:00 | `0 11 * * *` | Crear casos recurrentes del día |
| `daily_digest` | 07:30 lun–vie | `30 12 * * 1-5` | Resumen por Telegram (por analista y para ADMIN) |
| `nightly_maintenance` | 23:00 | `0 4 * * *` | Estancamiento, métricas (refrescar vistas materializadas), integridad de caja (saldo vs. libro), expirar recomendaciones, limpieza de trabajos, exportación de Storage |

**Reglas de alertas**

- **Estancamiento**: `now() − last_activity_at` mayor que el `sla_days` del proceso (o el umbral global), considerando prioridad, dependencias y estados que pausan el conteo (p. ej. `ON_HOLD`), configurable por estado.
- **Deduplicación**: `notifications.dedupe_key = tipo:entidad:destinatario:fecha`; no se repite la misma alerta el mismo día.
- **Preferencias por usuario**: canal (app / Telegram) y tipos de alerta.

**Telegram**

- Vinculación con código de un solo uso (`/vincular 123456`) que expira en 10 minutos → `telegram_links`.
- Mensajes **mínimos**: número de caso, tipo de alerta y enlace a la app. **Nunca** nombres de cliente, montos ni contenido de documentos (los bots de Telegram no ofrecen cifrado de extremo a extremo).
- Token secreto en el webhook, cola con *throttling* para respetar los límites de envío y respaldo en notificación dentro de la app.

## 11. Observabilidad, backups y continuidad

- **Logs estructurados** (JSON) con `request_id` de extremo a extremo (Vercel → Render → Supabase). Sentry (o equivalente) en web y engine.
- **Métricas clave**: latencia y tasa de `FAILED` en generación, trabajos `DEAD`, costo de IA, latencia de consultas del dashboard.
- **Monitor externo** (UptimeRobot, BetterStack u otro) sobre Vercel y `GET /healthz` de Render, con aviso directo por Telegram/correo. Un sistema no puede avisar de su propia caída, por eso `service_integrations` no basta.
- **Pantalla de monitoreo (MVP)**: solo salud y latencia. Uso/límites de Vercel, Render y Supabase requieren tokens de administración; se agregan después con tokens de solo lectura.
- **Backups**: Supabase Pro (diarios, 7 días). Habilitar **PITR** si se exige RPO menor a 24 h (recomendado por caja chica y auditoría). Como los backups nativos no incluyen Storage, agregar exportación nocturna de buckets y un `pg_dump` cifrado hacia un almacenamiento independiente del proveedor.
- **Prueba de restauración trimestral**, con registro del resultado. Definir RTO/RPO objetivo (D8).
- **Migraciones seguras**: patrón *expand/contract* (agregar → migrar → retirar) y plan de reversa por migración.
- **Retención**: particionar `audit_logs` por mes cuando crezca y archivar por política.
- **Runbook** breve para: falla de LibreOffice, caída del proveedor de IA (modo solo reglas), Supabase no disponible, cola con trabajos `DEAD`.

| **IA** | Conjunto dorado (≥ 50 casos), regresión por `prompt_version`, inyección de instrucciones, modo degradado |

| **Seguridad** | Checklist OWASP ASVS nivel 2 antes de producción, escaneo de secretos y dependencias en CI |

## 13. Plan de construcción para Antigravity

### 13.1 Protocolo de trabajo

- **Una fase por rama** (`feat/fase-N-tema`), con PR y checklist de aceptación de la fase.
- Antes de codificar: el agente lee `AGENTS.md`, `docs/v1.md` y `docs/v2.md` (secciones indicadas), propone un plan y **espera aprobación** en todo cambio de esquema, seguridad o caja.
- Contratos primero: tipos y esquemas zod en `packages/shared` antes que pantallas o endpoints.
- Si se usan varios agentes en paralelo, asignarles carpetas distintas (SQL y RLS / `apps/web` / `services/engine`) para evitar conflictos.

Plantilla de prompt por fase:

```text
Lee AGENTS.md, docs/v1.md (secciones: <...>) y docs/v2.md (secciones: <...>).
Objetivo: Fase <N> — <nombre>.
1) Propón un plan por pasos y espera mi aprobación.
2) Implementa en la rama feat/fase-<N>-<tema>: migraciones, RLS, tipos, UI y pruebas.
3) No toques producción ni pidas claves reales; usa .env.example.
4) Termina con el checklist de aceptación de la fase marcado y los comandos para verificarlo.
```

## 14. `AGENTS.md` (copiar a la raíz del repositorio)

````markdown
# AGENTS.md

## Proyecto
Sistema de gestión de casos, documentos, workflow y caja chica.
Fuente funcional: docs/v1.md. Fuente técnica: docs/v2.md. Anexo docs/v2.1.md (prevalece sobre v2.0; v2.0 sobre v1).

## Stack
- Web: Next.js (App Router), TypeScript estricto, Tailwind, shadcn/ui, TanStack Query, react-hook-form + zod, next-intl (es-PE) -> Vercel
- Engine: Node + TypeScript (Fastify), docxtemplater, LibreOffice headless, Docker -> Render
- Datos: Supabase (PostgreSQL, Auth, Storage, Realtime, pg_cron, pgvector)
- Pruebas: Vitest, Playwright, pgTAP
- Gestor de paquetes: pnpm (monorepo: apps/web, services/engine, packages/shared, supabase)

## Reglas no negociables
- Nunca ejecutar comandos contra producción. Solo local o staging. No pedir ni escribir claves reales: usar .env.example.
- Todo cambio de esquema es una migración nueva en supabase/migrations. Nunca editar migraciones ya aplicadas.
- Toda tabla en public tiene RLS habilitada, políticas y prueba pgTAP.
- service_role jamás en apps/web ni en variables NEXT_PUBLIC_*.
- audit_logs y cash_movements son append-only: correcciones con reversos, nunca UPDATE/DELETE.
- La IA solo recomienda: sale validada con zod contra el conjunto de candidatos de las reglas y nunca escribe en la BD por sí misma.
- Archivos solo en Storage privado; descargas por URL firmada emitida por el engine y auditadas.
- Lógica de avance y del DSL de reglas solo en packages/shared, con pruebas unitarias.
- Código e identificadores en inglés; textos de interfaz en español (es-PE) vía i18n; moneda PEN; zona America/Lima.
- Accesibilidad nivel AA y diseño responsive (móvil primero).
- Prohibido escribir listas fijas de negocio en el código (tipos de documento, personas, prioridades, estados, categorías, roles). Se leen de catálogos, workflow_statuses o settings. La lógica usa categorías semánticas y permisos, nunca etiquetas ni nombres de rol.
- La RLS usa private.has_permission() y private.feature_enabled(). Todo elemento configurable tiene is_active (toggle); nunca DELETE de configuración en uso.
- Los secretos solo en variables de entorno. Nunca leer, imprimir ni commitear .env. Usar .env.example.

## Flujo de trabajo
1. Leer las secciones de docs relevantes a la tarea.
2. Proponer un plan y esperar aprobación si toca esquema, RLS, seguridad o caja.
3. Trabajar en la rama feat/fase-N-tema con cambios pequeños y commits convencionales.
4. Ejecutar lint, typecheck, pruebas unitarias, pgTAP y e2e antes de abrir el PR.
5. El PR incluye el checklist de aceptación de la fase.

## Comandos
- pnpm dev | pnpm lint | pnpm typecheck | pnpm test | pnpm e2e
- supabase start | supabase db reset | supabase test db | supabase gen types typescript --local

## Calidad
- Archivos <= 300 líneas, funciones <= 30 líneas, sin console.log (usar logger estructurado).
- Validar con zod toda frontera (formularios, API, respuesta de IA, variables de entorno).

## Detenerse y preguntar cuando
- Una regla de negocio de v1/v2 sea ambigua o contradictoria.
- El trabajo dependa de una decisión pendiente (docs/v2.md sección 15).
- El cambio afecte RLS, caja chica, auditoría o el envío de datos a la IA.
````
